## Top findings (ranked, this component)

1. **Missing unstructured fallback for Action.Other lines (label/reset/merge/exec)** — 🟠 HIGH · git4idea · Effort: M
   When a user rebases a --rebase-merges or rebase.updateRefs=true scenario, git4idea falls back to a plain text editor if ANY structural line is present (GitInteractiveRebaseEditorHandler:115), giving the user full control to hand-edit label/reset/merge/exec lines. We ALWAYS show the commit-list-only UI and silently preserve structural lines via transformRebaseTodo, so the user can NEVER hand-edit them. For most users (no stacked branches, no merges), this is dormant. For stacked-branch power users who need to reorder label/reset/merge blocks by hand, this is a usability gap. **Recommendation:** Add a "detected structural lines — edit as text?" fallback flow in RebaseService.startInteractiveRebase (parse the todo, if ANY line is Action.Other, offer a button to open the raw todo in a text editor instead of the commit-list UI). File: src/git-core/RebaseService.ts:89–127, src/rebase/RebaseEditor.ts:89–113; git4idea GitInteractiveRebaseEditorHandler.java:115–117.

2. **Sequence-editor plan tampering (unauthenticated JSON in env)** — 🟡 MEDIUM · mixed · Effort: S
   The interactive rebase plan travels as `INTELLIG_REBASE_PLAN=<JSON>` in the environment. If an attacker can modify the env BEFORE git spawns the sequence editor (requires prior code execution in extension host OR a malicious git binary), they can inject a different plan (drop all commits, reorder maliciously). There is no HMAC or signature on the plan. **Accepted risk for most deployments** (requires prior compromise), but mark as a follow-up for high-security environments: generate a per-session secret (in-process only), compute HMAC of the plan, verify in rebaseTodoEditor.ts:56 before applying. File: src/git-core/RebaseService.ts:455, src/git-core/rebaseTodoEditor.ts:52–56.

3. **Interactive todo editor missing richness (detail pane, diff preview, keyboard shortcuts)** — 🟡 MEDIUM · platform · Effort: L
   IntelliJ's GitInteractiveRebaseDialog shows a commit-detail pane (full message, author, date) + inline diff preview + keyboard shortcuts (P/R/E/S/F/D mnemonics). Our RebaseEditor webview has dropdown-per-commit + drag-to-reorder, but NO detail pane, NO diff preview, NO keyboard shortcuts (user must click dropdown). This is polish, not a blocker — the dialog EXISTS and works (user can reorder, squash, drop). Flagged per NORTHSTAR.md P4 platform-rebuild tier. File: src/rebase/RebaseEditor.ts:349–918; git4idea GitInteractiveRebaseDialog.

## Security review (this component)

1. **Sequence-editor .sh shim + shellQuote** — ✅ SECURE. Process.execPath + editorJsPath are shell-quoted via POSIX `'\''` idiom (src/git-core/RebaseService.ts:476–478). Install paths can contain spaces/apostrophes; the escaping is standard. Script is written atomically via atomicWriteFileSync (no symlink traversal) with mode 0o755, cleaned up in try/finally. No user-controlled input in the script template.

2. **Sequence-editor argv injection** — ✅ SECURE. Plan travels via `INTELLIG_REBASE_PLAN` env var, not argv (git appends only the todo-path to argv, which we never shell-escape — read directly by fs.readFileSync). Hash values in the plan are matched via prefix-based case-insensitive compare (rebaseTodo.ts:54–58 hashMatches); git emits only `[a-f0-9]`, no shell metacharacters. No argv injection surface.

3. **Sequence-editor plan tampering** — 🟡 ACCEPTED RISK (see Top Finding #2). The plan JSON in env is unauthenticated. Attack requires prior extension-host compromise OR a malicious git binary (both are trust-boundary breaches). Recommendation: add HMAC verification for high-security deployments.

4. **Rebase continue/skip/abort error leakage** — ✅ CLEAN. BranchOps.rebaseContinue/Skip:532–556 surfaces git errors via `failureReason` field, sanitized through `sanitizeGitError` (removes credential-pattern substrings per gitError.ts). RebaseService paths return structured `IRebaseResult` (status enum, conflicts array, rebaseInProgress boolean). No raw git stderr/stdout leakage to toasts. Conflict file paths are user-controlled (repo content) but HTML-escaped in RebaseEditor:272–280 _conflictMessage and dialog rendering.

5. **Interactive rebase session lifecycle** — ✅ CLEAN. RebaseService `_sessions` is a private `Map<string,IRebaseSession>` keyed by repo.rootUri.fsPath. Planning sessions (pre-execution) are cleared on abandon (RebaseEditor:948–954 _clearAbandonedSession). Phantom-session reconcile (per memory #18) added in continueRebase:264–266 / skipCommit:348–350 / abortRebase:325 — `isNoRebaseInProgressError` detects "no rebase in progress" fatal and clears the stale session instead of surfacing the error. No session leakage across repos.

**Overall verdict:** Rebase security posture is sound. Sequence-editor argv/shell-injection surfaces are closed. Plan-tampering is an accepted low-severity risk (requires prior compromise). No credential leakage. One non-blocking enhancement available (HMAC on the plan JSON).
