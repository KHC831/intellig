## Top findings (ranked, this component)

1. **Fetch remote argv injection (BLOCKER)** — `RemoteOps.fetch:99` passes `options.remote` as positional arg with NO `buildGitArgs`/`--end-of-options` guard and NO leading-dash validation. A malicious remote name like `-c protocol.ext.allow=always` injects git config. Callable from PushDialog retry, PullDialog, AutoFetch (5min background loop), manual `intellig.fetch` — all surface repo.remotes from user-editable .git/config. **Severity: 🔴 security/blocker.** Source: git4idea (uses `--end-of-options`). **Effort: S (one 10-line guard or rewrite to buildGitArgs).** **Files:** `src/git-core/ops/RemoteOps.ts:68-114` (fetch method), contrast with `:171-211` (pull — uses buildGitArgs correctly) + `:214-258` (push — uses buildGitArgs + PushDialog validates refspec). **Fix:** either (a) `if (!options.remote || options.remote.startsWith('-')) throw new Error('Invalid remote')` before `:99`, OR (b) rewrite to `const refs = options.remote ? [options.remote] : []; const args = buildGitArgs('fetch', flags, refs);` (mirrors pull structure). Option (b) preferred (consistent with pull/push; scales to future refspec arg).

2. **Fetch/pull credential leakage (SECURITY REGRESSION)** — `RemoteOps.fetch:106-114` + `pull:210` throw raw git stderr without `sanitizeGitError`. When auth fails, `fatal: unable to access 'https://user:ghp_token123@github.com/...'` leaks token into toast (if caller toasts the error) AND into logger output channel (`AutoFetchService.ts:136 logger.error(err)` logs raw Error.message → OUTPUT CHANNEL contains credentials). Push is protected (PushDialog:314 sanitizes before row error). **Severity: 🔴 security.** Source: n/a (IntelliJ sanitizes at IDE log-appender level; we must do per-op). **Effort: S (3 sites: wrap fetch/pull throws, sanitize AutoFetch logger call).** **Files:** `src/git-core/ops/RemoteOps.ts:106-114` (fetch throw), `:210` (pull throw), `src/sync/AutoFetchService.ts:136` (logger leak). **Fix:** RemoteOps methods catch + `throw new Error(sanitizeGitError(rawError.message))`, OR every call-site catches + sanitizes before toasting/logging (defense-in-depth = both). AutoFetchService `:136` must be `logger.error(sanitizeGitError(err instanceof Error ? err.message : String(err)))`.

3. **Rejected-push strategy dialog (HIGH daily-hit feature)** — IntelliJ shows modal (Merge / Rebase / Cancel) on non-ff push rejection + loops atomically (push → rejected → update → retry → ..., max 10 rounds). Persists choice. Our PushDialog offers per-row "Pull and Retry…" button (:608) but **doesn't auto-push after pull** — user must manually re-click Push. ONE retry round only (no loop). NO modal strategy choice (Update Project hard-codes `--rebase`). **Severity: 🟠 high (daily collab workflow).** Source: git4idea (`GitPushOperation.java:148-196` push-attempt loop + `GitRejectedPushUpdateDialog.kt`). **Effort: M (wire auto-push callback from PullDialog.show → PushDialog re-submit; add modal for Merge vs Rebase; loop until success/cancel/max-attempts).** **Files:** `src/sync/PushDialog.ts:873-894` (pullAndRetry handler — opens PullDialog but doesn't chain push), `src/sync/updateProject.ts` (hard-codes rebase), need new `src/sync/RejectedPushStrategyDialog.ts` (modal). **Design:** PullDialog.show returns Promise<"success"|"cancelled">; on "success" PushDialog._submitRows([row], 'push') again. Loop in _submitRows (attempt counter, max 10). Modal = 3-button vscode.window.showWarningMessage with "Remember choice" → globalState.

## Security review (this component)

### 🔴 CRITICAL (2 findings — both BLOCK merge/release)

1. **Fetch remote argv injection** — RemoteOps.fetch:99 passes `options.remote` positional with no `buildGitArgs` guard. Exploit: edit .git/config remote name to `-c protocol.ext.allow=always` → next auto-fetch (5min loop) or manual fetch injects config. Pull/push use buildGitArgs (safe); fetch does NOT (vulnerable). **Fix: rewrite fetch to use buildGitArgs OR add leading-dash guard before :99.**

2. **Fetch/pull credential leakage** — RemoteOps.fetch:106 + pull:210 throw raw stderr → auth failures leak `https://user:token@host` into toast + output channel (AutoFetchService:136 logs raw). Push sanitizes (PushDialog:314); fetch/pull do NOT. **Fix: catch + sanitizeGitError before throw/log.**

### ⚪ VERIFIED SAFE (3 areas)

- **Push refspec argv injection:** PushDialog.buildPushOptions:195-200 validates `isValidPushRef` (leading `-`/`.` rejected) + RemoteOps.push:256 uses buildGitArgs → `--end-of-options` spliced. Defense-in-depth OK.
- **Pull argv injection:** RemoteOps.pull:209 uses buildGitArgs. PullDialog sources remote/branch from repo.branches (git-provided, not arbitrary input). Safe.
- **Remote set-url/rename argv guards:** RemoteOps:291/309 guard leading-dash on name/URL. No `--end-of-options` (git remote subcommand doesn't support it), but guard sufficient (mirrors branch/tag name policy). Safe.

### 🟡 CONFIRMED NO-ISSUE (false-alarm investigation)

- **Home-dir path leakage:** `gitError.ts:66-114` redacts `/Users/<name>/`, `/home/<name>/`, `C:\Users\<name>\` → `~/`. Applied to push errors (PushDialog:314). NOT applied to fetch/pull yet (see credential-leakage finding above — same fix covers both). Once fetch/pull sanitize, home-dir leakage also closed.
